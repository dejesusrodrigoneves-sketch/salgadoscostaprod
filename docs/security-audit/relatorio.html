Esta auditoria identificou 11 achados de segurança no projeto SIC-IA, incluindo 2 vulnerabilidades críticas que permitem acesso não autenticado a dados pessoais de clientes (IDOR) e destruição de dados cross-tenant. Pontos Fortes

SF-1: Todas as rotas admin/superadmin validam roles no backend com authenticate + authorize('superadmin'). O gateway de permissão no navegador é cosmético — o backend é o guard real.
SF-2: Função escapeHtml() completa (&, <, >, ", ') é usada consistentemente em admin.js, cart.js, menu.js, filiais.js para dados de usuário em innerHTML.
SF-3: Proxy routes (mapbox, geoapify, graphhopper) têm allowlist de paths + rate limit + serviços hardcoded. SSRF mitigado.
SF-4: Webhooks (ASAAS, iFood, Keeta, Food99) verificam tokens em headers. Autenticação adequada.
SF-5: Nenhuma API key ou secret hardcoded no código-fonte. Todos os segredos via process.env.
SF-6: JWT_SECRET não tem default inseguro — env.js:5 retorna undefined se não setado. Falha visível no startup.

--- ISSUE 1 ---

[Segurança] IDOR crítico — buscarPedido expõe dados de clientes sem autenticação

Labels: security, critical

Problema: A rota GET /api/public/pedidos/:id não possui autenticação. Qualquer pessoa pode acessar dados pessoais de qualquer pedido (nome, telefone, endereço, CEP) bastanto incrementar o ID sequencial.

Evidência: backend/src/controllers/publicController.js:462-468

exports.buscarPedido = asyncHandler(async (req, res) => {
  const empId = requireTenant(req, res);
  if (!empId) return;
  const pedido = await sql.buscarPedido(req.params.id, empId);
  if (!pedido) return res.status(404).json({ error: 'Pedido não encontrado' });
  res.json(pedido);  // ← Sem autenticação!
});

Impacto: Vazamento de dados pessoais de clientes (LGPD). Qualquer pessoa pode enumerar pedidos.

Sugestão de correção: Adicionar authenticatePublic e filtrar por clienteWhatsapp.

Critérios de aceite:

  • [ ] Rota requer Bearer token válido
  • [ ] Usuário só acessa seus próprios pedidos
  • [ ] Teste E2E verifica que pedido de outro usuário retorna 404

--- ISSUE 2 ---

[Segurança] Destruição cross-tenant — deleteMany sem filtro em processedWebhook

Labels: security, critical

Problema: Ao deletar uma empresa, processedWebhook.deleteMany({ where: {} }) deleta TODOS os webhooks processados de TODAS as empresas, causando perda de dados cross-tenant.

Evidência: backend/src/repositories/empresaRepository.js:36

prisma.processedWebhook.deleteMany({ where: {} })  // ← Sem filtro de empresaId!

Impacto: Perda de dados de webhook para todas as empresas. Webhooks podem ser reprocessados.

Sugestão de correção: Adicionar filtro { where: { pedido: { empresaId } } } ou remover esta linha se processedWebhook não tem relação com empresa.

Critérios de aceite:

  • [ ] deleteMany filtra por empresaId
  • [ ] Teste verifica que deletion não afeta outras empresas
